# ALVIS オフラインファースト・マルチデバイス計画

最終更新: 2026-11-04
対象ブランチ: `development`
対象リポジトリ: `doka100-ui/ALVIS-PWA`

## 1. 最終目標

ALVISは特定の端末やOSに固定しない。iPhone、iPad、Windows/macOS/LinuxのPC、将来的にはAndroidでも利用できる個人用AIを目指す。

基本原則:
- 会話、推論、記憶、音声入出力の主要機能は、可能な限り端末内で完結させる。
- 初回セットアップ・モデル取得・更新・端末間同期にはインターネットを使ってよい。
- 必要なアプリ資材とモデルを端末へ保存した後は、ネット接続なしでも使える状態を目指す。
- オフライン利用を妨げる外部APIを必須にしない。クラウド機能は任意の補助とする。
- 端末性能に合わせてモデルと処理方式を選び、同じ記憶形式・会話仕様・設定を維持する。
- 端末間同期は接続時だけ行い、競合時に一方のデータを無断で上書きしない。

## 2. 対応端末の方針

| 端末 | 優先する実行方式 | 注意点 |
|---|---|---|
| iPhone | PWA / Safari、端末性能に応じた軽量モデル | メモリ、発熱、バックグラウンド制限、WebGPU対応を実機検証 |
| iPad | PWA / Safari、WebGPU対応時はローカル推論 | モデルサイズとSafariのメモリ上限を検証 |
| PC | PWA / 対応ブラウザ、WebGPUやローカル実行環境 | GPU/メモリに応じて高性能モデルを選択 |
| Android（将来） | PWA / 対応ブラウザ | 端末・ブラウザごとの互換性を検証 |

「どの端末でも同じ巨大モデルを動かす」ことは前提にしない。端末ごとに適切なモデルを選び、ALVISとしての人格、設定、承認済み記憶、会話データを共通化する。

## 3. 現在の実装と未達成事項

### すでにあるもの
- 統合PWA画面 `index-integrated.html`
- WebLLM `@mlc-ai/web-llm@0.2.87` と Qwen3-4B Q4 のブラウザ内/WebGPU推論
- AES-GCMによる端末内暗号化保管庫
- 暗号化バックアップ/復元
- 任意の暗号化クラウド同期
- ブラウザ標準Speech Synthesisによる読み上げ

### まだ完全オフラインではない理由
- WebLLMライブラリを `https://esm.run/` から読み込むため、アプリ起動時の依存コード取得がネットワークに依存する可能性がある。
- Qwen3-4Bモデルは初回ダウンロードが必要。キャッシュ保持の修正はあるが、iOS Safariを含む全端末で永続保持できるかは未検証。
- Service Workerは現状アプリの基本ファイルをキャッシュするが、全依存ライブラリ・モデル資材のオフライン再利用を保証していない。
- ブラウザ標準音声はOS/ブラウザの音声エンジンとインストール済み音声に依存し、端末間で同じ声・オフライン動作を保証できない。
- iPhone/iPad/PCで同一のWebGPU機能・メモリ容量が使えるとは限らない。
- オフライン状態での初回起動、再起動、モデル読み込み、ストレージ削除/容量不足からの復旧は端末別に検証が必要。

## 4. 目標アーキテクチャ

```
ALVIS共通アプリ / PWA
  ├─ 共通UI・会話仕様・人格設定
  ├─ 記憶/履歴/暗号化保管庫（端末内）
  ├─ AI実行アダプター
  │    ├─ WebGPU対応端末: WebLLM等
  │    ├─ 制約のある端末: 対応する軽量ローカル推論方式
  │    └─ 対応不可端末: ローカル定型機能と明示的な機能制限
  ├─ 音声アダプター
  │    ├─ 端末標準音声（オフライン可否は端末依存）
  │    └─ Kokoro等の端末内TTS（日本語品質・端末互換性を検証して採用）
  ├─ オフライン資材管理
  │    ├─ アプリシェル/依存コード
  │    └─ ダウンロード済みモデル・音声資材
  └─ 任意のオンライン機能
       ├─ 暗号化端末間同期
       └─ アプリ/モデル更新
```

アプリのコード、AIモデル、音声モデルは別々に管理する。アプリ更新で巨大なAIモデルのキャッシュを誤って消さない。モデルは容量・互換性・バージョンを表示し、ユーザーがダウンロード/削除を管理できる設計を目指す。

## 5. 開発フェーズ

### Phase 0: 現状調査（進行中）
- 既存の依存ライブラリ、Service Worker、PWAマニフェスト、モデルキャッシュ、ストレージ方式を調査。
- 既存データ形式・暗号化・同期APIを保護する。
- 端末ごとのWebGPU・ストレージ・音声機能の制約を整理する。

### Phase 1: オフライン起動基盤
- アプリシェルと必要なJavaScript依存コードを、利用許諾と更新方式を確認したうえでローカル配信/キャッシュできる構成へ移す。
- オフライン時のナビゲーションと静的ファイル取得を正しく処理するService Workerにする。
- 初回オンライン起動→必要資材取得完了→オフライン再起動のテストを行う。
- 既存のQwenモデルキャッシュとALVISアプリキャッシュを分離する。
- 既存の保管庫・暗号化・バックアップ・同期形式は変更しない。

### Phase 2: 端末別AI実行
- 起動時にWebGPU等の機能・メモリ条件を調べる。
- 端末ごとに利用可能なモデルを提示し、非対応時は原因と代替手段を表示する。
- iPhone、iPad、PCで軽量モデルから段階的に検証する。
- モデル取得済み端末でネットワークを切り、会話・再起動・再読み込みを試験する。

### Phase 3: オフライン音声
- 現在の端末標準Speech Synthesisをフォールバックとして維持する。
- Kokoro等の日本語対応TTSを別候補として、ライセンス、モデル容量、実行速度、音質、iOS Safari互換性を検証する。
- モデルを端末へ保存し、ネットワークなしで試聴・読み上げできることを確認してから本体に統合する。
- 音声認識も将来は端末内方式を優先する。

### Phase 4: 共通記憶と端末間同期
- 各端末でローカル動作することを優先し、同期はオンライン時の任意機能とする。
- 既存の暗号化同期・revision/競合制御を維持する。
- 端末ごとにモデルや音声設定を分けつつ、ユーザーが選んだ共通設定・記憶は同期できるようにする。
- 同期トークンや暗号鍵を平文で保存しない。

### Phase 5: 実機テストと安定化
- iPhone Safari、iPad Safari、PCブラウザで個別に確認。
- 初回ダウンロード、機内モード起動、会話、記憶の保存/再読込、音声、アプリ再起動、容量不足、更新後のキャッシュ保持を試験。
- ユーザーの実機確認が済むまで完了扱いにしない。

## 6. 安全・開発ルール

- 作業は `development` ブランチのみ。本番 `main` は明示許可なしに変更しない。
- 変更前に必ず現行コードを取得する。
- 既存の `ALVIS_ENCRYPTED_V1`、PBKDF2/AES-GCM、バックアップ形式、同期Worker/APIは別途明示的な設計・承認なしに変更しない。
- 外部音声APIへ会話文を送る方式を必須にしない。原則ローカルTTS。
- APIキーをブラウザコード、LocalStorage、Gitへ保存しない。
- 一度に大きな変更をしない。各段階で差分とテスト結果を記録する。
- 静的コード確認と実機確認を区別し、未検証の互換性を断言しない。
- オフライン対応は「PWAとして画面が開く」だけでは完了としない。AI推論・記憶・音声までネットなしで動くかを機能ごとに検証する。

## 7. 現在の次の一歩

Phase 0として、現行 `index-integrated.html` の外部依存、WebLLMモデル取得/キャッシュ、Service Worker登録、マニフェスト、音声読み上げ処理を調べる。調査後、最初の小さなコード変更としてオフライン起動に必要な依存資材とService Workerの改善範囲を決める。調査だけで安全性を確認できない変更は実装しない。
