# ALVIS 開発・運用ガイド

最終確認日: 2026-11-04

## 1. GitHubとブランチ

- リポジトリ: `doka100-ui/ALVIS-PWA`
- 通常の開発対象: `development`
- 本番ブランチ: `main`（明示的な許可なしに変更・マージ・デプロイしない）
- `sync-test`: 既存ブランチ。developmentとは履歴が分岐しているため、指示なくマージしない。
- 開発URL: https://development.alvis-pwa.pages.dev/index-integrated.html
- 本番URL: https://alvis-pwa.pages.dev/

## 2. 開発環境

- ユーザーはプログラミング未経験。操作案内は日本語で一つずつ行う。
- 主な実機: iPad Pro M1 Safari。iPhone 17 Pro Maxも使用。
- 現行AI: WebLLM `@mlc-ai/web-llm@0.2.87` / `Qwen3-4B-q4f16_1-MLC`。
- AIはWebGPUで端末内推論。初回モデル取得はネットワークが必要。
- 8Bモデルは過去にiPad Safariでクラッシュしたことがあるため、4Bを標準とし、8Bを本体の標準にしない。

## 3. 変更の標準手順

1. `HANDOFF.md` と必要な仕様資料を読む。
2. 作業対象ブランチが `development` であることを確認。
3. 対象ファイルの最新内容をGitHubから取得する。過去のチャットにあるコードを現行版とみなさない。
4. 変更対象と影響する機能を短く説明する。
5. 既存機能・保存データへの影響を確認する。
6. 変更は小さく、一つの目的に限定する。
7. `development` にのみコミットする。
8. コミットSHAと変更ファイルを確認する。
9. 開発URLでユーザーに実機テストを一つずつ案内する。
10. 結果を `CHANGELOG.md` と `HANDOFF.md` に反映する。

## 4. 絶対に守るルール

- `main`、本番URL、`sync-test` を無断で変更しない。
- ユーザーの明示的な許可なしに既存機能を削除・仕様変更しない。
- LocalStorageの `ALVIS_ENCRYPTED_V1`、暗号化方式、既存データ形式を無断変更しない。
- 同期Worker URL/API、Bearer認証、revision/競合制御を無断変更しない。
- バックアップ・復元処理を無断変更しない。
- ユーザーの実機テスト前に「修正成功」「完成」と断定しない。
- パスワード、同期トークン、秘密情報をコード・資料・コミットへ記載しない。
- 実データを消去する操作、LocalStorageの初期化、アプリ再インストールを安易に案内しない。
- コードを大きく再掲せず、ファイル名・関数名・変更概要・コミットSHAを中心に報告する。

## 5. テストの基本セット

変更内容に応じて、最低限次を確認する。

- 保管庫の解除・ロック。
- AIモデルの読み込みと短い会話（例: 1+1）。
- 記憶候補の抽出、承認、長期記憶表示。
- 再ログイン後の記憶保持。
- 暗号化バックアップの作成。復元試験は安全なテストデータで行う。
- クラウド同期状態確認、保存、競合時の停止挙動（変更が同期に関係する場合）。

すべてを毎回実行する必要はない。変更した機能と影響範囲に応じて選び、未実施のテストを明記する。

## 6. 変更記録

各変更について `CHANGELOG.md` に以下を記録:
- 日付
- 対象ブランチ
- コミットSHA
- 変更したファイル
- 目的・変更内容
- 既存データ/機能への影響
- テスト結果（ユーザー確認済み / 未確認）

## 7. 新しいチャットでの再開

次のメッセージを送る:

> ALVISの開発を再開します。GitHubの `doka100-ui/ALVIS-PWA` にある `development` ブランチを使用してください。最初に `docs/HANDOFF.md` と必要な仕様資料を確認し、現在の開発状況を把握してから作業してください。既存機能を勝手に変更・削除せず、変更前に必ず現状のコードを確認してください。操作は一つずつ案内してください。

最初に `HANDOFF.md`、必要に応じて `ALVIS_SPEC.md`、`ARCHITECTURE.md`、`DEVELOPMENT.md`、`CHANGELOG.md` を参照する。過去チャットを完全に再現するのではなく、資料と現行コードを正として作業する。
